## Context

当前 `concise`、`balanced`、`detailed` 对长字幕仍走单次 `_generate_directly` / `_generate_with_pdf_reference`，三档只有附加提示词不同，没有可机械验证的证据分配、覆盖和审计。通用安全清洗最多保留 50,000 字符；本轮三条真实基线去时间戳正文为 36,427～40,914 字符，均未触发截断，但更高语速或更长素材仍存在尾部被静默丢弃的结构性风险。`exhaustive` 已经改为全量证据、全局蓝图、分章写作、全局审计和局部修复，但若把这条高成本流水线原样复制给低档位，会破坏用户需要的成本和速度阶梯。

本变更必须在代码改动前保存三条真实基线，改动后用另外三条时长相近的视频复测。配对样本如下：

| 档位 | 修改前 | 时长 | 修改后 | 时长 | 差异 |
|---|---|---:|---|---:|---:|
| concise | 一百七十三回「OpenClaw」 | 149.31 分钟 | 一百九十三回「Codex 合并进入 ChatGPT」 | 150.38 分钟 | 0.71% |
| balanced | 一百九十回「世界如棋」 | 153.04 分钟 | 一百八十六回「AI 落地的两极分化」 | 153.16 分钟 | 0.08% |
| detailed | 一百七十八回「消费品出海营销策略」 | 154.59 分钟 | 一百九十一回「vibe coding 从 0-1 解读课伴」 | 155.42 分钟 | 0.54% |

不同主题视频不能用于证明事实覆盖绝对等价，因此端到端数据只用于工程性能与产物特征比较；质量还需结合高价值主题抽样、结构、重复和内部标记泄漏检查。

## Goals / Non-Goals

**Goals:**

- 三档均消费全部有效字幕，建立可机械验证的内容地图和章节蓝图，不再依赖一次生成和固定字符截断。
- 共享超详细的事实优先、先规划后写作、稳定前缀、确定性门禁和局部修复原则。
- 通过档位策略控制证据重要度、章节数量、批次大小、输出预算和审计强度，形成稳定的质量/成本阶梯。
- 对真实任务记录调用数、缓存命中/未命中输入 Token、输出 Token、费用、节点耗时和结构质量。
- 保持现有 API、任务快照、PDF 参考、截图、输出语言和 usage callback 兼容。

**Non-Goals:**

- 不修改 `exhaustive` 生产路径，不恢复 `thorough`。
- 不实现跨任务持久化内容地图缓存；只通过稳定消息前缀利用供应商 prompt cache。
- 不调整 ASR、思维导图或前端视觉，不新增模型或依赖。
- 不把绝对字数作为质量结论，也不把费用目标做成任务失败条件。

## Decisions

### D1：共享一个 profile-driven 生成器，不复制三套流程

新增内部 `DetailProfile` 配置，至少包含证据重要度范围、章节范围、每章要点范围、每次写作包含的章节数、map/draft/audit Token 上限、审计模式和最终结构下限。`concise`、`balanced`、`detailed` 走同一组解析、规划、写作、校验和修复函数，仅由 profile 决定取舍。

替代方案是复制 `exhaustive` 三份后分别删减；这会产生四套近似实现和难以同步的 bug，因此不采用。

### D2：一次全量内容地图作为低成本理解层

对不超过 500,000 字符的三档长字幕，第一次调用以完整、经注入防护但不截断的字幕生成严格紧凑 JSON 内容地图。证据与术语使用定长数组，章节使用短键，避免长课程因重复 JSON 字段触及输出上限。地图包含标题、总览、术语、证据项和章节：证据项具有稳定 ID、重要度、类型、原文摘录、摘要和置信度；章节包含 ID、目标、要点和证据映射。任务标题仅作为 ASR 专名校正线索，不能作为事实证据。

超过安全全文阈值时，降级为现有全量分段证据能力或显式失败，不得静默截断。对当前约 150 分钟样本使用全文理解，复用已真实验证过的 500,000 字符上限。

替代方案是三档都先做多段证据提取；覆盖更强但低档位首轮费用过高。一次全文地图已经足够支撑有选择的三档，详细档通过更高证据数量和更严审计弥补。

### D3：稳定消息链最大化 DeepSeek prompt cache

内容地图调用的完整字幕提示词、模型返回的地图 JSON构成稳定前缀。后续各写作批次均在相同前缀末尾追加“当前批次章节”指令，不重复构造顺序不同的长 prompt。JSON 修复、章节修复同样只接在已有消息链末尾。

这会让首次全文输入通常计为未命中，后续批次的大块字幕和地图有机会计为缓存命中。所有调用继续由 `_call_llm` 上报真实 usage，不用理论值代替。

### D4：证据重要度是档位差异的权威来源

- `concise`：固定选择 18 条 critical/high 独立证据；3～4 章；每章正文目标 350～650 字；一次生成全部章节；不保留非必要案例；默认无语义审计。
- `balanced`：固定选择 30 条 critical/high/代表性 supporting 证据；5～6 章；每章正文目标 550～900 字；每批最多 3 章；代表性案例和必要推导各保留一层；仅在确定性门禁或低置信度条件触发时审计/修复。
- `detailed`：固定选择 50 条 critical/high/supporting/重要 context 证据；6～8 章；每章正文目标 850～1400 字；每批最多 2 章；保留定义、推导、重要案例、数据、边界和注意事项；执行一次紧凑全局审计并按需修复。
- `exhaustive`：维持当前全部非噪声证据、逐章生成、全局审计和定向修复。

档位定义的是素材内证据覆盖，不要求模型补齐素材不存在的案例、数据或边界。

### D5：章节批处理控制调用数

简洁的全部章节可在一次写作调用中完成；适中每次最多生成三章；详细每次最多生成两章。每个批次必须对分配的证据 ID 输出可剥离覆盖声明，代码逐章核验。相比逐章一调用，批处理减少请求次数；相比单次直接生成，地图和证据声明提高全局覆盖与可验证性。

约 150 分钟视频的正常调用目标（不含思维导图）为：简洁 2～3 次、适中 3～5 次、详细 5～8 次；格式修复和问题章节修复可能使调用数增加，目标不作为硬失败阈值。

### D6：程序门禁优先，语义审计按档位启用

所有三档检查唯一 H1、预期 H2、空章节、重复标题、证据覆盖声明、内部 ID/模板泄漏和 Markdown 围栏。简洁只在门禁失败时局部修复；适中在门禁失败或内容地图含低置信关键项时执行紧凑审计；详细固定执行一次只返回 JSON 问题列表的全局审计。详细审计只接受 `critical`/`high` 且属于事实、证据缺失、术语、无依据主张、实质重复或结构断裂的问题，并最多修复两个最严重章节，避免把风格偏好放大成付费重写。审计不得返回完整笔记，修复不得重写合格章节。

### D7：基线与复测保存为可审计 JSON 报告

基准报告记录阶段、档位、任务 ID、源文件、时长、任务状态、ASR/笔记节点时间、字幕字符数、笔记字符数、H1/H2/H3/表格数量、调用明细和汇总费用。费用优先使用任务保存的实际估算字段；若只有 usage，则使用仓库内同一套 DeepSeek 价格函数计算并注明。

为避免基准脚本包含凭证或绕开运行时设置，真实任务通过现有任务服务/API 创建和查询；报告不得写入密钥。

## Risks / Trade-offs

- [全文内容地图在小上下文模型上失败] → 500,000 字符安全上限外不静默截断；保留清晰错误或分段降级，单元测试覆盖全部字符进入某个理解阶段。
- [修改后三档费用高于旧的一次生成] → 真实基线正文没有触发截断，但一次生成缺少覆盖证明；通过章节批处理、稳定缓存前缀和档位证据预算，把质量可验证所需的新增费用控制在最低必要范围。
- [JSON 地图格式偶发不合规] → 固定证据数量并限制各字符串长度；语法错误沿同一消息链至多重写一次紧凑地图，章节逻辑错误只返回小型映射补丁；代码清理重复/未知映射并把补丁漏挂证据均匀补入最小章节，不再为机械缺口追加付费调用。
- [原生 JSON 模式影响缓存] → 真实复测表明 DeepSeek 的 JSON 模式与正文文本模式缓存隔离，导致首批正文长前缀从命中转为未命中，费用由约 ¥0.060 升至约 ¥0.090；三档因此保持统一文本模式和严格本地解析。
- [模型声称覆盖证据但正文没有表达] → 机械声明只做第一层门禁；详细固定全局审计，适中按风险审计，真实样本再做人工抽样。
- [详细档审计把轻微风格问题变成多次重写] → prompt 明确排除润色、轻微重复、篇幅偏好和可选补充；解析器只保留 critical/high 白名单问题并最多修复两个不同章节。
- [不同视频主题密度影响输出量] → 使用时长近似配对，并报告每万字幕字符的 Token、费用、输出长度和章节数，不只比较绝对值。
- [现有工作区有用户未提交改动] → 仅修改本变更范围文件，实施前后检查 diff，不覆盖无关改动，不提交或推送。

## Migration Plan

1. 创建并验证本 OpenSpec 变更，登记 Beads 任务。
2. 在任何生产代码改动前运行三个基线任务并保存报告和产物位置。
3. 先增加 profile、prompt 构建与解析/校验单元测试，再接入 `process()` 分流。
4. 跑三档定向测试后重建容器，使用三段新视频完成端到端复测。
5. 运行后端全量 pytest、前端构建和 OpenSpec validate；全部通过后关闭 Beads 任务。
6. 若真实复测出现质量退化或异常费用，回滚三档入口到原 `_generate_directly` / `_generate_with_pdf_reference`，保留基准报告用于下一轮分析；历史任务和数据库无需迁移。

## Open Questions

- 三档目标调用数和费用先作为真实测试目标，不在首次实现中固化为拒绝生成的硬预算；完成六视频数据后再决定是否写入默认产品提示。
- 跨任务持久化内容地图缓存可能进一步降低“同一视频切换档位”的费用，但需要版本、隐私、容量和失效设计，留作独立变更。
