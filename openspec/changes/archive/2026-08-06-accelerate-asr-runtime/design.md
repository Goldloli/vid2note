## Context

现有长音频会按在线 280 秒、本地 120 秒切片。每个任务各自创建 `_EngineResolver` 和 `WhisperCppEngine`；resolver 内的本地 semaphore 只能限制同一任务，不能限制不同任务。实测三条任务同时降级后，三个 faster-whisper 实例各自占满 CPU，单条耗时约从 173–197 秒增至 561–580 秒，三条总完工时间却没有改善。

另一个问题是 bcut 本地滚动额度只能描述本机已预留的调用，无法保证远端真实额度。多个任务可先后取得本地预算，然后同时让各自三个在线 worker 撞到 412；失败状态只在任务内共享，已在途请求仍会重复失败。

## Goals / Non-Goals

**Goals:**

- 额度不足时最多用一次串行探测确认远端状态，后续分段和任务快速降级。
- 本地 CPU Whisper 在整个进程内只允许一个任务持有执行槽，恢复单任务最快速度并降低平均完成时间。
- 在线额度正常时继续使用现有分段并发，不影响在线吞吐。
- 取消、异常和正常结束都可靠释放本地槽；指标能够解释等待、探测与冷却行为。

**Non-Goals:**

- 不改变模型、VAD 算法、识别文本或 SRT 拼接规则。
- 不引入 Redis、独立调度服务、GPU 或新配置页面。
- 不保证 bcut 的可用性，也不试图预测远端未公开的即时额度。

## Decisions

### D1：在 resolver 生命周期持有进程级本地执行槽

新增模块级 `BoundedSemaphore(1)`。resolver 第一次调用 Whisper 前以可取消轮询方式获取槽，并一直持有到 `transcribe_audio` 的 `finally` 调用 `resolver.close()`。这保证一个长任务的多个本地切片不会与其他任务交错争抢 CPU。

选择任务级租约而不是在 `WhisperCppEngine.transcribe()` 外增加全局锁，因为逐切片释放会让多个长任务轮流抢占，单条仍接近三倍延迟；任务级租约才能让第一条约 3 分钟完成、后续任务依次完成。保留引擎实例自身的锁，继续保护模型线程安全。

### D2：在线长音频先单飞探测，再放开并发

在线 profile 的多段任务先同步处理第一个分段。bcut 探测由进程级锁串行化；探测成功后，剩余分段按 `online_concurrency` 并发。若探测得到 412/429，resolver 标记 bcut 在本任务失效并降级，剩余分段不再发在线请求。

选择首个真实分段作为探测而不是额外生成短音频，避免新增 ffmpeg 开销和浪费额度；探测结果本身直接成为最终字幕的一部分。

### D3：把远端限流写入共享冷却状态

在现有 `bcut_budget` 中增加 `mark_rate_limited()` 和冷却查询。冷却同时写入进程内状态与缓存目录中的独立小文件，由现有文件锁保护；默认持续一个 12 小时滚动窗口。后续任务即使本地预留额度尚有余额，也会以 `remote_rate_limited` 原因拒绝在线路径。容器重启后仍可读取冷却文件。

选择独立冷却文件而不是修改现有预算 JSON schema，避免迁移既有预算文件和把远端失败伪装成本机已消费额度。

### D4：重复并发失败只记录一次降级

resolver 在锁内原子判断“是否首次把该在线引擎标为 failed”。只有首次 412/429更新共享冷却、增加 `degradation_count` 并输出结构化降级日志；已在途的重复失败直接使用本地后备，不重复计数。

### D5：增加可观测指标

ASR metadata 增加：是否执行在线探测、是否因远端冷却跳过、等待本地槽的秒数、是否取得本地槽。既有 `engine_success_counts`、`degradation_count` 和总耗时保持兼容。

## Risks / Trade-offs

- [健康在线任务增加一次串行首段等待] → 仅首段串行，成功后其余分段仍并发；多任务探测锁只覆盖真实首段。
- [12 小时冷却可能比远端实际恢复更保守] → 与已知滚动窗口一致，优先避免长任务反复撞限流；过期自动恢复。
- [一个异常缓慢的本地任务阻塞后续任务] → 保留现有任务取消与超时；所有出口在 `finally` 释放租约。
- [进程级 semaphore 不协调多容器] → 当前架构为单容器单进程；多实例部署不在 v1 范围。

## Migration Plan

无需数据库或 API 迁移。重建单容器后新调度立即生效；旧预算文件继续读取，冷却文件按需创建。回滚只需恢复 ASR 协调代码，SRT 与任务数据不受影响。

## Open Questions

无。本次固定本地任务槽位为 1，后续只有在真实硬件基准证明多槽能提升总吞吐时才考虑配置化。
