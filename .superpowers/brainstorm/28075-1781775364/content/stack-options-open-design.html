看完 Open Design 后：栈要不要换？

结论不是“全保留”也不是“全推倒”。如果你愿意承担一次真正的架构迁移，存在比当前栈更适合长期产品化的组合。

A

原栈强化 · 最快

Electron + Vue + FastAPI/Python；在 Python 中实现 CLI 检测、spawn、事件归一化和内置 Agent。

优点：现有复用最多，最快出 MVP。
代价：Open Design 的 TypeScript Agent Runtime 很难直接复用；前端仍是弱类型 JS，桌面控制面和媒体域继续混在 Python 服务里。

B

TypeScript 控制面 + Python 媒体 Sidecar · 推荐

Electron + React/TypeScript + Vite；Node Knowledge Daemon 负责 Vault、Agent、CLI、会话、审批和 SSE；Python Sidecar 只负责下载、FFmpeg、ASR 与 LLM 笔记流水线。

优点：最容易借鉴 Open Design；控制面全栈类型一致；Python 的媒体/AI 生态完整保留。
代价：需要重写 UI 和 API 边界，并维护 Node/Python 两个受管进程。

C

全 TypeScript · 不推荐

Electron + React + Node，媒体和 Agent 全部放进同一运行时；Python 只作为少数外部工具或彻底移除。

优点：语言统一，打包表面简单。
代价：本地 ASR、模型管理和现有 Python 资产损失最大；重写成本高，却没有增加用户价值。

应该借鉴 Open Design
  • 声明式 Runtime Registry
  • detect / auth / capability negotiation
  • CLI 输出归一为统一 AgentEvent
  • stdin / prompt file / argv 大小策略
  • cwd 沙箱、取消、超时、session resume
  • Mock CLI + 录制事件做无费用回放测试
  • 唯一 data-root 与共享 API contract
不应该照搬
  • Next.js：它服务于 Vercel/SSR；本地个人桌面不需要
  • 庞大的插件、设计系统和 artifact preview 体系
  • 22 个 CLI 首发支持；首版只做 Codex、Claude、内置 Agent
  • bypassPermissions 直接操作正式 Vault
  • 整个 monorepo 包拆分规模
  • 把 Agent 当事实裁判；Wiki 写入仍必须走 ChangeSet
推荐拓扑 B

Renderer（React/Vite）只连接 Knowledge Daemon；Daemon 管理 Vault 与 Agent，并通过一个稳定的 Job 协议调用 Python Media Sidecar。浏览器永远不直接访问 Python。这样 Agent 和知识库是一等公民，视频流水线成为可替换的来源处理器。
