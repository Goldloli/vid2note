方案 A · 目标架构

不是把所有能力塞进一条 Pipeline，而是形成四条相互解耦、可分别验证的链路。

1 · SOURCE PIPELINE
视频 URL / 本地视频 → 下载 → 音频 → SRT → 高质量来源笔记 → 原始素材归档
2 · WIKI COMPILER · 产品核心
读取新来源 + index.md + 相关 Wiki 页面 → 生成变更集 → 用户审批 → 原子写入 Markdown → 更新 index.md / log.md
3 · AGENT RUNTIME
问题 → 先读 index → 搜索相关页面 → 必要时回查来源与 SRT → 带引用回答 → 可将新洞见提交为 Wiki 变更集
4 · MEDIA CITATION
Wiki 引用锚点 → source_id + 时间区间 → 原视频 → 按需生成片段 / 截图 → 回答中内嵌播放

为什么可行

  • 现有下载、FFmpeg、ASR、Markdown 链路可复用
  • Wiki 本质是受约束的文件编辑 Agent
  • SRT 天然提供文字与视频时间轴映射
  • 所有阶段都能用确定性测试单独验收

真正困难的地方

  • 不是聊天，而是 Wiki 合并质量与长期一致性
  • 跨页修改必须支持预览、冲突检测和回滚
  • 时间码引用需贯穿 ASR、笔记和 Agent 输出
  • 知识规模增长后需要搜索，但不应首日上复杂 RAG

判断：技术可行性高；做出可靠 MVP 的概率约 80–90%，做成长期“越用越聪明”的优秀产品约 55–70%，主要变量是 Wiki Compiler 的提示词、评估集和审批体验。
