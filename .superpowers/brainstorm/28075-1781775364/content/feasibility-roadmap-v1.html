最终可行性与重构路线

产品价值很高，但前提是把“笔记质量 + Wiki 合并质量”作为核心指标，而不是功能数量。

价值判断

对视频重度学习者 / 研究者：高
把几十小时视频变成可积累、可追溯、可回看的主题知识。

对普通笔记用户：中等
如果只是写 Markdown，Obsidian 已足够；本产品不能靠“又一个编辑器”取胜。

真正差异化：
跨视频持续编译 Wiki + 每条结论可回到时间码、截图和视频证据。

概率判断

技术实现：90%+

可靠 MVP：80–85%

打磨成熟桌面产品：70–80%

形成长期复利体验：55–70%

最后一项主要取决于笔记评估集、Wiki schema、冲突处理和用户是否愿意审批，而不是模型 API 是否能调用。

阶段 0 · 先把旧资产变成可信基线

修复 data-root、配置旁路、真实并发与假 E2E；建立视频 → SRT → 来源笔记 Golden Dataset。验收：固定样本可重复产出，关键事实与时间码可量化评估。

阶段 1 · 新控制面骨架

建立 pnpm/TypeScript monorepo、Electron + React/Vite、Knowledge Daemon、共享 contracts；把现有 Python 包装成受管 Media Sidecar。验收：新 UI 可启动/停止 Sidecar，并完整跑通旧视频任务。

阶段 2 · Vault 与来源证据

落地 raw/sources/wiki/index/log 协议、source_id、文件哈希、时间锚点和按需 FFmpeg 片段。验收：任意来源笔记的关键结论都能一键跳回正确视频区间。

阶段 3 · Wiki Compiler · MVP 核心

实现 index-first 关联、结构化 ChangeSet、Diff 审批、原子写入、回滚和 lint。验收：第二个同主题视频能增强既有 Wiki 页面，并明确标记补充、重复或矛盾。

阶段 4 · Agent Runtime

借鉴 Open Design 的 Runtime Registry 和 AgentEvent；先做内置 Agent、Codex、Claude 三个适配器。验收：Agent 回答前读取 index/Wiki，引用可追溯；任何写回都生成 ChangeSet。

阶段 5 · 完整知识工作台

完成四区可调布局、Markdown 编辑、Agent 证据卡、媒体工具、Wiki lint 和设置中的 A/B/C 自治模式。知识图谱、其他文档格式、云同步、多 Agent 全部延后。

必须建立的护城河

  • 来源笔记质量评估集
  • Wiki 更新的可解释 Diff
  • 每条主张的时间证据
  • 用户反馈能反哺 schema 与 prompt

最高风险

  • 漂亮摘要但事实不可靠
  • 页面越多，schema 越漂移
  • CLI 版本变化导致适配器脆弱
  • 双 Sidecar 打包和生命周期失控
  • 过早追求 Obsidian 全功能复刻
