选择重构路线

三条路线都能实现目标，区别在于风险、速度和产品边界。点击你倾向的方案。

A

渐进式模块化演进 · 推荐

保留 Electron / Vue / FastAPI 和现有视频流水线，新增 Vault、Wiki Compiler、Agent Runtime、Media Citation 四个边界清晰的模块，再逐步替换旧页面。

复用率高 · 首个闭环最快 · 可分阶段验证 · 需要先偿还路径配置和任务模型债务

B

新内核重写

保留算法经验和部分适配器，重新设计领域模型、数据库、任务系统和前端壳，再迁移旧流水线。

边界最干净 · 长期维护舒服 · 交付周期更长 · 容易在重写期失去现有可用闭环

C

Obsidian 插件 + Python Sidecar

直接把 Obsidian 作为主界面，插件负责审批、聊天和媒体引用，Python 服务继续处理下载、ASR 与 FFmpeg。

最快获得成熟 Wiki UX · 图谱和生态现成 · 产品受 Obsidian API 与分发方式约束 · 难以形成独立应用体验

我的判断

A 最符合当前资产：它不是在旧房子上无限加层，而是先把承重墙重新划清，再一间一间改。B 的技术诱惑很大，但现阶段收益不抵风险；C 适合作为未来兼容入口，而不是产品主体。
